# 长文本翻译模型多轮对比报告

测试日期：2026-09-12 至 2026-09-13
测试对象：Qwen 自建服务、Z.AI GLM、MiniMax 官方服务
测试文本：`SAIT - Stan Grad Centre 2.txt`，29,510 字符、821 行，原文含 602 个 `*` 标记

## 1. 测试方法

- 三个模型使用同一份英文转录文本和同类提示词，目标语言为简体中文。
- 主测试采用整篇一次性提交，不拆分、不重试，`max_tokens=10000`。
- 后续轮次显式关闭或抑制推理；GLM 使用 `thinking.type=disabled`。
- 记录 HTTP 状态、服务端实际模型、总耗时、结束原因、输出行数及标记数量。
- 行数和 `*` 数量用于衡量格式保真，不直接等同于翻译质量。
- 质量结论来自结构检查及开头、中段、结尾抽查，不是专业人工逐句盲评。

## 2. 原始结果

### 第一轮：整篇提交

| 模型 | 耗时 | HTTP / 结束状态 | 输出行数 | `*` 数量 | 结果 |
|---|---:|---|---:|---:|---|
| Qwen | 103.8 秒 | 200 / stop | 819 | 599 | 成功 |
| GLM 5.3 Flash（关闭推理补测） | 136.5 秒 | 200 / stop | 809 | 734 | 成功 |
| MiniMax M3 | 46.9 秒 | 200 / stop | 817 | 776 | 成功 |

GLM 5.3 Flash 默认推理模式另有一次失败实验：174.1 秒后虽然 HTTP 200，但 10,000 个输出 token 中 9,993 个用于推理，正文为空，`finish_reason=length`。这不是模型不能翻译，而是翻译任务不应启用深度推理。

### 第二轮：统一关闭或抑制推理

| 模型 | 耗时 | HTTP / 结束状态 | 输出行数 | `*` 数量 | 结果 |
|---|---:|---|---:|---:|---|
| Qwen | 120.3 秒 | 200 / stop | 820 | 588 | 成功 |
| GLM 5.3 Flash | 132.9 秒 | 200 / stop | 806 | 702 | 成功 |
| MiniMax M3 | 48.3 秒 | 200 / stop | 818 | 814 | 成功 |

同轮额外测试 GLM 5.3 非 Flash：87.2 秒，812 行，586 个 `*`，正常翻译到结尾。

### 第三轮：最终候选横向测试

| 模型 | 耗时 | HTTP / 结束状态 | 输出行数 | `*` 数量 | 结果 |
|---|---:|---|---:|---:|---|
| Qwen | 125.3 秒 | 524 / 无正文 | 0 | 0 | Cloudflare 超时 |
| GLM 5.3 | 85.3 秒 | 200 / stop | 818 | 623 | 成功 |
| MiniMax M3 | 63.1 秒 | 200 / stop | 1 | 817 | 成功，但整篇被合并成一行 |

### GLM 分段补充实验

GLM 5.3 Flash 将 821 行拆成 11 组、每组约 80 行串行翻译，全部请求成功，总耗时 161.8 秒，合并后 816 行。分段改善了整篇请求的换行保留，但比一次性提交慢，而且模型仍会合并少量行。第一次尝试让 80 行以 JSON + ID 返回时，模型生成了非法 JSON，说明结构化结果必须校验，不能默认可信。

## 3. 汇总评价

### Qwen 自建服务

- 三轮整篇测试中成功 2 次、HTTP 524 超时 1 次；成功耗时平均 112.1 秒。
- 成功输出的行数最接近原文，第一轮 `*` 数量也最接近原文，抽查中文表达较自然。
- 最大问题不是模型不会翻译，而是非流式长请求经过 Cloudflare：成功时间已经接近 125 秒代理读取超时，一旦服务器排队或生成速度稍慢便返回 524。
- 不适合作为当前“整篇、非流式、同步等待”主通道。

### GLM 5.3

- 非 Flash 版两次整篇测试均成功，耗时 87.2 秒和 85.3 秒，平均 86.2 秒，波动小。
- 第三轮输出 818 行、623 个 `*`，在该轮中结构最接近原文。
- 必须关闭推理；默认推理会消耗大量 token，却可能不产生翻译正文。
- 当前三者中，稳定性、速度和格式保真的综合表现最好。

### MiniMax M3

- 三轮 HTTP 请求全部成功，平均耗时 52.8 秒，是速度最快的模型。
- 前两轮分别输出 817 和 818 行，但第三轮把全文压成一行，格式行为不稳定。
- 多轮中经常增加大量 `*`；较早的结构化分批测试还出现过返回 ID 与输入 ID 不一致。
- 适合做快速备用模型，但结果必须通过严格的段 ID 校验。

## 4. 问题分析

1. 整篇翻译成功不等于字幕结果可直接使用。三个模型都曾改变换行或标记；字幕必须保持每个时间段与译文一一对应。
2. `max_tokens=10000` 不是当前主要瓶颈。成功请求通常只使用约 5,700 至 6,600 个输出 token，并以 `stop` 正常结束。
3. 推理模式不适合纯翻译。它增加延迟和 token 消耗，GLM 默认推理实验已经证明可能挤占全部输出预算。
4. Qwen 的 524 是访问链路问题。Cloudflare 已连接源站，但约 125 秒内未收到响应；增加客户端超时不能解决代理超时。
5. 单次整篇请求缺少可恢复性。任何超时、断网或格式异常都会使整篇结果作废，无法从中间继续。
6. 仅依赖换行是不可靠的。模型可以合并或拆分行，必须携带稳定 ID，并在程序端校验 ID 集合、顺序和数量。

## 5. 最终方案

### 模型顺序

1. 主模型：GLM 5.3，显式设置 `thinking.type=disabled`。
2. 第一备用：MiniMax M3，关闭或尽量抑制推理，只在严格校验通过后采用结果。
3. 第二备用：Qwen。保留用于质量对照和本地/私有部署，但当前不使用整篇非流式请求。

### 生产调用方式

- 不采用整篇一次性同步请求作为正式字幕翻译流程；它只适合作为性能基准。
- 按字幕段落组成中等批次，建议初始值 40 至 60 段，并严格串行，避免服务端并发拥堵。
- 每个输入段携带数字 ID，要求模型返回 `{id, text}`；程序校验 ID 数量、集合、顺序、空译文和重复项。
- 每批成功后立即原子保存缓存。失败时只重试当前批，不重翻已完成批次。
- JSON 解析失败或 ID 不匹配时，将当前批缩小一半重试；仍失败则切换备用模型。
- 所有模型关闭推理；翻译提示词固定版本并写入缓存签名，避免提示词变化后误用旧缓存。
- Qwen 若继续承担长请求，应改为真正流式响应、后台任务 ID，或绕开 Cloudflare 代理；否则每批必须控制在明显低于 125 秒的范围。

## 6. 验收标准

- 每个原文段必须恰好对应一个译文段，ID 完整率 100%。
- 任一批次不得出现空译文、重复 ID、未知 ID 或未解析 JSON。
- 成功批次可以断点恢复，程序重启后不重复调用 API。
- 单批目标耗时低于 60 秒；超过阈值记录告警并允许缩小批次。
- 最终 SRT 的时间轴和英文段落不被模型修改，仅替换或附加中文文本。
